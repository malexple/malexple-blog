# Как я подключил индекс своего Java-проекта к Perplexity через собственный MCP-сервер

*Короткий рассказ о том, как из консольной утилиты, которая строит индекс кода в SQLite, получился MCP-сервис на VPS с HTTPS, обновлениями патчами и подключением к Perplexity.*

## Зачем это понадобилось

У меня есть утилита **Indexer**. Она обходит Java-проект, разбирает исходники в AST и складывает всё в один файл SQLite: файлы с текстом, типы и члены с номерами строк, вызовы, зависимости, модули Gradle, полнотекстовый поиск. Раньше этот файл приходилось прикладывать к каждому чату с ИИ-ассистентом вручную. После каждой правки кода нужно было заново прикладывать актуальную версию.

Хотелось другого: чтобы ассистент сам ходил в актуальную базу, а после правок на сервер уходило только то, что изменилось.

## Что получилось

Схема из трёх частей:

1. **Indexer** (локально) строит индекс и умеет делать инкрементальные патчи.
2. **mcp-sql-service** (на VPS) хранит базу и отдаёт её по протоколу MCP через Streamable HTTP.
3. **Perplexity** подключается к сервису как кастомный удалённый коннектор.

Сервис отдаёт восемь инструментов, и все они только читают: `index_info`, `find_type`, `context`, `read_source`, `read_lines`, `search`, `callers` и `sql`. Ассистент начинает с `index_info`, находит тип через `find_type`, смотрит обзор через `context`, а текст читает по диапазону строк, не открывая файл целиком.

## Шаг 1. Проверка локально

Сначала я убедился, что всё работает на своей машине. Сборка (`./gradlew clean test`) прошла с `BUILD SUCCESSFUL`. Затем я проиндексировал проект Manuscriptium: 586 файлов, 710 типов, 5378 членов, 0 ошибок. Запросы к локальному MCP-сервису вернули ожидаемое: восемь Gradle-модулей и граф зависимостей между ними. Одна неочевидная вещь: зависимости `app → :core` и `app → :editor` в графе дублировались. Причина оказалась простой: они объявлены в разных конфигурациях Gradle, поэтому в запросе нужен `DISTINCT`.

## Шаг 2. Патчи вместо полной загрузки

Полная база проекта весит мегабайты, а после правки двух файлов меняется несколько строк. Поэтому инкрементальный прогон с `--patch-dir` пишет маленький патч вида `patch-5-6.sql.gz`, а `push --patch-dir` отправляет его на сервер.

Тут я наступил на главные грабли: каждый запуск индексатора увеличивает номер версии `seq`. Патч применяется только к серверу, который стоит ровно на предыдущей версии. Мой первый патч `4→5` не применился: сервер всё ещё был на `seq 1`, потому что я ни разу не загрузил полную базу после очередного полного прохода. Правило оказалось простым:

- после полного прохода всегда сначала `push --db`;
- между загрузкой и патчем не запускать индексатор лишний раз;
- если цепочка разошлась, загрузить базу заново.

После загрузки полной базы патч `5→6` применился с первого раза: `applied patch-5-6.sql.gz`, сервер на `seq 6`.

## Шаг 3. Домен, Docker и HTTPS

Для публичного адреса я купил домен `mcp-sql.com` и поднял сервис на VPS (Debian 13). Развёртывание вместилось в три файла:

- `docker-compose.yml` с двумя сервисами: сам MCP-сервис и Caddy;
- `Caddyfile` из трёх строк: `reverse_proxy mcp-sql:8080`;
- `.env` с доменом и двумя случайными ключами, для чтения и для записи.

Сервис наружу не торчит: он слушает порт 8080 только внутри Docker-сети, а в интернет смотрят порты 80 и 443 Caddy, который сам получает и продлевает сертификат Let's Encrypt. Образ я собрал локально и выложил в Docker Hub, так что на сервере остаётся `docker compose pull && docker compose up -d`.

Маленькая ошибка по дороге: в плане адрес был `mcp.mcp-sql.com`, а работать начал `mcp-sql.com`. Я поправил `MCPSQL_DOMAIN` в `.env` и пересоздал контейнеры. Простого перезапуска для этого мало: переменные из `.env` подхватываются при пересоздании.

## Шаг 4. Подключение к Perplexity

В Perplexity нужен тариф Pro, Max или Enterprise. Дальше **Plugins → Add custom → Add MCP connector → Remote**: имя `Indexer`, адрес `https://mcp-sql.com/mcp`, транспорт Streamable HTTP, сеть Public.

По умолчанию в форме стоит аутентификация **OAuth**, а наш сервис её не поддерживает. Нужно выбрать **API Key** и вставить ключ чтения. Ключ записи в коннектор не кладётся никогда: он только для утилиты `push` на моём компьютере.

После подключения в настройках коннектора появились все восемь инструментов в режиме Allow, а первый вызов `index_info` вернул данные моей базы: workspace `indexer`, 107 файлов, 126 типов, 1004 члена.

## Что я бы сделал так же

- **Только чтение.** Сервис не умеет менять код. Подсказки вроде `readOnlyHint` не защита, а пожелание сервера, поэтому настоящая защита — это отдельные ключи и отсутствие инструментов записи.
- **Два ключа.** Ключ чтения передаётся в клиент, ключ записи живёт только на моей машине и на сервере.
- **Периодический полный проход.** Инкрементальный режим не пересчитывает зависимые файлы, поэтому `calls.resolved` и `type_deps` могут устареть. Индекс сам пишет об этом в `notes`, а полный проход рекомендован после 100 изменений.
- **Один том для данных.** Базы лежат в томе `mcp-data`, а `docker compose down -v` удалил бы и их, и сертификаты, поэтому ключ `-v` я не использую.

## Итог

Теперь после правок я запускаю инкрементальный прогон, отправляю патч размером в пару килобайт и спрашиваю ассистента про актуальный код. Весь проект, включая документацию, лежит в репозитории: README есть на английском и на русском.

*Стек: Java 21, SQLite с FTS5, JavaParser, Gradle, Docker Compose, Caddy, MCP через Streamable HTTP.*
